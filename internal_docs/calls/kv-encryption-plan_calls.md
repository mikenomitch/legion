# Judgement Calls: KV Encryption Plan

Decisions made while writing
[`plans/kv-encryption-plan.md`](../plans/kv-encryption-plan.md), before any
code exists. **Entries are ranked by project impact, highest first — the
number is the rank.** Implementation-time calls get inserted at their rank as
the phases execute; if a citation elsewhere names an entry by number, fix it
when you renumber.

## 1. On by default, with a root key the manager mints itself

**Call.** `encryption.enabled` defaults to `true` on every cluster, new or
upgraded. With no config at all a manager mints a 32-byte root key at
`<storePath>/keys/root.key` (`0600`) on first start and encrypts every KV
write from then on. Existing plaintext rows stay readable until a rewrap
converts them, so an upgrade changes nothing an operator can observe except
`legion keyring status` and the contents of the `value` column.

```console
$ legion start manager
INFO Minted KV root key rk_9f31c2a7e0d4b6a1 at /var/lib/legion/keys/root.key
INFO KV keyring unlocked: 1 data key (dk_01J8ZQ…), provider=file
```

**Alternatives.** (a) Off until configured, the Kubernetes posture — nothing
changes on upgrade, no new file to lose, no `state query` regression. (b) On
for clusters bootstrapped by this release, off for older stores — a sticky
per-store default.

**Trade-off.** Every default cluster now has a second thing that must survive
a host loss: the root key file. A backup restored onto a fresh host without
it is a locked keyring, not a working cluster, and `legion state query` over
KV values returns ciphertext from the first encrypted write. Both are
mitigated (the backup CLI prints where the key is and that it is *not* in
the backup; restore refuses up front and names the path; the plan's upgrade
gate keeps a mixed-version cluster un-encrypted rather than broken) but
neither is free. (b) was rejected outright because "is it on? depends on when
you bootstrapped" fails the 3am test.

**Why (simplicity, and it is the point).** The feature exists so a leaked
copy of the store is not a leaked credential set; a default that leaves 95%
of clusters plaintext does not deliver that. Docker Swarm encrypts raft logs
by default with a key on disk and makes autolock the opt-in hardening; Nomad
encrypts variables unconditionally. Kubernetes' off-by-default is the
cautionary tale, not the model. Evidence that would reopen this: real users
who run KV as a queryable config store and lose `state query` over it — the
`enabled = false` switch and `rewrap --plaintext` exist for exactly them.

## 2. The root key lives outside the store; the data keys live inside it, wrapped

**Call.** Two tiers. Data keys (`dk_…`) are generated by the leader, wrapped
by the root key, and stored in the replicated `keyring_key` table like any
control-lane row. The root key (`rk_…`) is held by a provider — a file on
each manager, an env var, or an external KMS via `exec` — and is never
written into the database, a changeset, a snapshot, or a backup in any
provider.

**Alternatives.** (a) Nomad's default: the KEK itself in raft "in
cleartext", so a snapshot is self-contained and restore never needs a
separate file. (b) One tier — a single key file per manager with values
encrypted directly under it (plan §11, alternative B): no keyring table, no
RPCs beyond status.

**Trade-off.** Two concepts to explain (root key, data key) where (b) has one,
and a new replicated table. Multi-manager clusters must get the root key onto
every manager (Phase 1: by hand, like `clusterSecret`; Phase 4: on join).
Against (a): a lost root key means lost values, which Nomad's default cannot
suffer.

**Why (simplicity in the operations that happen often; the threat model in
the ones that matter).** The thing that must be identical on every manager
(the root key) changes rarely; the thing that changes on every rotation (the
data key) is replicated, so a rotation is one raft write and no file is
touched on N hosts — (b) makes every rotation a coordinated multi-host config
change with a window where managers disagree about the key. Against (a): a
backup that decrypts itself is exactly the artifact this plan exists to
neutralize; HashiCorp's own docs warn the default "may expose data in case of
a breach". Nomad 1.9 and Kubernetes KMS v2 both landed on wrapped-DEKs-in-
storage, KEK-outside after trying the alternatives, which is strong evidence
the shape is right.

## 3. Every KV value is encrypted, not a flagged subset

**Call.** There is no `--secret` flag and no reserved `secrets/` prefix.
With encryption enabled, every `kv_entry.value` is ciphertext.

**Alternatives.** (a) A per-entry `secret = true` flag (or a path
convention) so ordinary config values stay plaintext and remain queryable
through `legion state query`. (b) Encrypt per ACL-style path selectors in the
manager config.

**Trade-off.** `state query` and the State Explorer lose the ability to
inspect KV values at all, including feature flags and other non-secret
config, and there is no way to opt a value out short of `enabled = false`
for the whole cluster. A future "queryable KV" need would have to be met by
a KV-side query, not SQL.

**Why (simplicity, and it closes the hole completely).** A flag means the
security property depends on nobody ever forgetting it — the exact class of
mistake (a password `kv put` without `--secret`) that a human under time
pressure makes. Encrypt-all makes the guarantee one sentence: "no KV value is
on disk in plaintext." It also fully closes the `state:read` bypass of KV
path ACLs (`docs/auth-and-acls.md`, "`state:read` is powerful"): raw SQL
sees ciphertext for *every* row, not for the rows someone remembered to
flag. Kubernetes encrypts a whole resource type (`secrets`) for the same
reason; Nomad encrypts every variable.

## 4. A missing root key locks KV; it does not stop the manager

**Call.** When the store holds keyring rows the provider cannot unwrap, the
manager still starts, joins raft, schedules, and serves every non-KV RPC.
KV reads and writes fail with a `FAILED_PRECONDITION` that names the root
key id, the provider, the path checked, and the manager; `legion keyring
status` lists every key that cannot be unwrapped; `legion_keyring_unlocked`
reads `0`; `/readyz` is unaffected. The one exception is `--restore-from`,
which refuses to proceed — an operator is present and the action is
explicit.

```console
$ legion kv get prod/db/password
error: keyring locked: root key rk_9f31c2a7e0d4b6a1 (file provider) is not
available at /var/lib/legion/keys/root.key on manager mgr-b. Copy it from a
manager that has it, or set LEGION_ROOT_KEY.  (FAILED_PRECONDITION, retryable: true)
```

**Alternatives.** (a) Refuse to start — Docker Swarm's autolock behavior
("without it you will not be able to restart the manager"); nothing runs in
a half-configured state. (b) Vault's sealed state: the process runs but
serves *nothing* until unsealed.

**Trade-off.** A cluster can run for a long time with one manager quietly
unable to serve KV, and a KV-driven re-render on that manager fails in the
logs rather than at a human. The gauge and the status command are the
mitigation, and an operator who wants (a) can alert on the gauge.

**Why (simplicity at 3am).** Losing a manager — and with it possibly
quorum — over a missing file is a worse incident than KV failing loudly on
that manager. The scheduler, heartbeats, rollouts, and every job that does
not touch KV keep working; the responder gets one error that says which file
to copy. (b) would take down everything to protect one table.

## 5. Keyring initialization is gated on every raft voter being upgraded

**Call.** In raft mode the leader does not create the first `keyring_key`
row — and therefore never performs an encrypted write — until every voter
advertises a manager protocol version that includes this feature. Until
then `legion keyring status` reports `pending-upgrade` and writes are
plaintext, exactly as before the upgrade. `local_disk` has no peers and no
gate.

**Alternatives.** (a) A documented rule only: "upgrade all managers before
the first KV write", like the `plan_candidates = 0` guidance for the
format-2 rows. (b) An explicit `legion keyring init` that the operator runs
once the roll is complete; nothing automatic.

**Trade-off.** A new keyring state to explain, a dependency on per-voter
version data in the membership view (which Phase 1 may have to add), and a
cluster whose upgrade stalls halfway is silently un-encrypted for as long as
it stays that way (the status command says so, but nobody is forced to
look). (b) contradicts entry 1 — default-on that requires a command is
opt-in with extra steps.

**Why (correctness under the standard rolling upgrade).** Unlike every
previous schema-adding release, this feature would write to the new table
*by itself, at startup*, on the first upgraded manager to win an election; a
changeset touching `keyring_key` or `kv_entry.enc_key_id` cannot be applied
by a manager that has not migrated, and a doc rule cannot stop a startup
write. Nomad gates its keyring migration on "after all servers are upgraded
to 1.9.0"; Legion's edge boot already fences on the worker's advertised
`protocolVersion`. Same mechanism, same reason.

## 6. AES-256-GCM through the already-linked `ring`, with a time-and-count rotation guard

**Call.** Values are AES-256-GCM (96-bit random nonce, 128-bit tag) via
`ring::aead`, which Legion already links through `jsonwebtoken`, `rustls`,
`rcgen`, and `object_store`. The active data key rotates at
`dataKeyRotationAge` (default `720h`) and, as a safety net, after 2³¹
encryptions since the leader loaded it — half the NIST SP 800-38D bound for
random IVs. The counter is in-memory per process.

**Alternatives.** (a) XChaCha20-Poly1305 (192-bit nonce): random nonces
are safe for any practical number of messages, so no count guard at all —
but a new crate (`chacha20poly1305`) and an algorithm outside the FIPS
list. (b) Kubernetes KMS v2's construction: derive a single-use key per
value with HKDF over the data key plus 32 random bytes, which also removes
the bound at the cost of 32 extra bytes per value and a second primitive to
explain.

**Trade-off.** The guard is a small piece of machinery whose only job is to
enforce a bound that time-based rotation makes unreachable (2³¹ writes in
30 days is ~830 writes/s sustained, for a KV whose writers are humans and
agents), and its counter resets on restart, so the bound is enforced per
process rather than per key lifetime. Documented as an accepted
approximation. Also: `ring` is not a FIPS-validated module, so "AES-GCM" buys
an approved *algorithm*, not a validated implementation; the doc says so.

**Why (simplicity and the persona that asks for the feature).** Zero new
dependencies in a binary the project actively keeps small, hardware
acceleration for free, and the algorithm every comparator uses (Vault, Nomad,
Kubernetes, AWS) — which matters because the operators who require
encryption at rest are disproportionately the ones whose checklist names
AES-256-GCM. The guard costs ~20 lines; (a) would cost a dependency and an
argument with an auditor; (b) would cost an explanation.

## 7. External KMS through an `exec` provider, not linked SDKs

**Call.** The only way to keep the root key in AWS KMS, GCP KMS, Azure Key
Vault, Vault Transit, an HSM, or `systemd-creds` is
`rootKey = { provider = "exec", command = [...] }`: a process contract of
`wrap` / `unwrap` / `describe` over JSON on stdin/stdout, a conformance
harness (`legion keyring provider test`), and reference plugins under
`plugins/keyring/` that shell out to the vendor CLI. Providers are called
only at start, on keyring changes, and on rotation — never on a KV read or
write.

**Alternatives.** (a) Native providers linked into the binary, one per
vendor (Nomad's `awskms`/`azurekeyvault`/`gcpckms`/`transit` blocks).
(b) A gRPC plugin socket like Kubernetes' KMS plugin interface.

**Trade-off.** An extra process and a vendor CLI on every manager host; a
provider implemented as a shell script is easier to get subtly wrong than a
typed SDK call, which is why the harness exists; no per-vendor knobs
(region, role assumption) in Legion's config — they live in the command.
(b) was rejected for now as heavier than the need; the JSON contract can grow
a socket transport later without changing the operations.

**Why (extensibility without weight).** Every cloud SDK is a large
dependency tree, and each is a release-cadence liability the project would
own forever; the `exec` contract is one interface that covers every KMS that
exists and every one that does not yet. It is the same seam Legion already
uses for volume plugins, with the same conformance-harness discipline. If a
native provider ever earns its place it slots in behind the same trait.

## 8. Ciphertext is bound to its key path

**Call.** The GCM additional authenticated data is the KV key path. A
ciphertext copied from `prod/db/password` into `dev/scratch` — where an
attacker has `kv:read` and, via `state:write`, can write raw rows — fails
authentication and reads as `Corrupt`, never as the secret.

**Alternatives.** (a) Nomad's choice: bind the key *id* only. (b) Bind the
path *and* the version, which would also refuse a rolled-back ciphertext
replayed at a new version.

**Trade-off.** Renaming a KV key is not a row update; it is a decrypt and
re-encrypt (there is no rename today, so nothing changes). Against (b): a
principal with `state:write` can replay an old ciphertext at the same path,
and this plan does not stop that — `state:write` can already rewrite any
row, including the version, so the marginal defense was judged not worth
binding the version into every read path.

**Why (a cheap closed door).** AAD is free — one argument to `seal`/`open` —
and it turns a transplant attack into an integrity error. SOPS binds the
path, AWS Secrets Manager binds the ARN, Nomad binds the key id; binding
the identity of the secret is the settled pattern.

## 9. Rewrap runs automatically after every rotation

**Call.** After a rotation (scheduled, guard-triggered, or `legion keyring
rotate`) the leader re-encrypts every value under the new active key in the
background — batches of 256 rows, one replicated write per batch, throttled —
without bumping `version` or `updated_at` and without touching the reactive
path, then garbage-collects the retired key once nothing references it.
`legion keyring rewrap` also runs it on demand.

**Alternatives.** Nomad's shape: rotation alone leaves old keys in place
indefinitely; re-encryption is a separate, explicit `rotate -full`.
Kubernetes: a manual `kubectl replace` loop.

**Trade-off.** Background write traffic on the control lane after every
rotation (bounded by KV size, which is small), and a rewrap that is running
when leadership moves restarts on the new leader. An operator who wanted
rotation *without* re-encryption (to keep old ciphertext stable for some
external reason) cannot have it.

**Why (simplicity).** The keyring converges to one active key on its own. A
retired key that lingers for months because nobody ran the second command
is precisely the state that makes "rotate after an offboarding" a lie; the
whole point of rotation is that old key material stops mattering, and that
only happens once nothing is encrypted under it.

## 10. The rendered copies are named residual exposure, not encrypted here

**Call.** This plan encrypts `kv_entry.value` only. The rendered results of
`$` references and `{{ kv "…" }}` templates in `job_config` / `task_config`
rows, the worker's state file, and task directories stay as they are, and
the public doc says so in a numbered list (plan §6.9).

**Alternatives.** (a) Extend the keyring to the derived columns now
(`task_config.env`/`files`, `job_config.config`, and while at it
`signing_key.private_key_pem`). (b) Move template rendering to the worker so
the manager never materializes secrets — Nomad's `template` + Variables
model, Kubernetes' kubelet-side secret mounts.

**Trade-off.** A user who reads only the headline could believe their
secrets are encrypted at rest when a rendered copy is one `state query`
away in `task_config`. The doc's job is to prevent that reading; the
`state:read` hole is only *partly* closed until the follow-up lands.

**Why (scope, honestly).** (a) touches the scheduler's read-model cache
(`cached_task_configs_for_job_config`), the changeset projection on
followers, and every consumer of task configs; (b) reshapes the shipped
KV-reactive design. Either is its own plan with its own trade-offs, and the
choice between them (encrypt derivatives vs. stop creating them) should be
made on its own evidence rather than smuggled in here. Encrypting the source
of truth is independently valuable — it is what makes backups and replicas
safe — and it builds the keyring the follow-up will reuse.

## 11. `state:read` sees ciphertext and gets no decrypting helper

**Call.** `legion state query`, saved queries, and the UI State Explorer
return the `value` column as stored: base64 ciphertext plus `enc_key_id`.
There is no SQL function, view, or flag that decrypts.

**Alternatives.** A `kv_decrypt(value, key)` SQL function or a `kv_plain`
view, available to principals holding both `state:read` and `kv:read`.

**Trade-off.** Operators who used raw SQL to inspect KV values lose that;
`legion kv get` / `kv list` are the replacement, and they are filtered by KV
path ACLs.

**Why (security boundary, and it is the free win).** The bypass being closed
is precisely "raw SQL reads every KV value regardless of `paths`"; a
decrypting helper reopens it by another door and would need its own path-
scoped enforcement inside the SQL surface to be safe. Keeping SQL blind
keeps the invariant one sentence: KV values are readable through the KV API
and nowhere else.

## 12. Ciphertext is base64 in the existing `TEXT` column, plus `enc_key_id`

**Call.** No new value column and no magic prefix. `value` holds
`base64(nonce ‖ ciphertext ‖ tag)`; `enc_key_id` (`NULL` for plaintext
rows) says which key and, through the keyring row, which algorithm.

**Alternatives.** (a) A `value_ct BLOB` column beside a nulled `value` —
no base64 overhead. (b) A self-describing prefix (`lgnenc1:…`) in `value`
alone — no schema change beyond nothing.

**Trade-off.** 33% size overhead from base64 on values that are small by
nature; a second column to keep in step with `value` on every write.

**Why (explainable).** A `state query` result is a string a human can read
("that's base64, and there's the key id"), the migration is one `ALTER TABLE
ADD COLUMN`, and legacy plaintext rows are distinguishable with no
ambiguity — (b) is ambiguous the moment a user stores a value that happens
to start with the prefix, and (a) makes the raft changeset and the State
Explorer carry blobs for no gain at KV sizes.

## 13. The root key file is one key per line — the first wraps, every line unwraps

**Call.** `root.key` is base64, one 32-byte key per line, `#` comments
allowed. The first line is the wrapping key; every line is tried for
unwrapping. Root-key rotation is "generate → prepend on every manager →
`root-key rewrap` → delete the old line", and the file is re-read on rewrap
and on an unknown-root-key unwrap failure, so no restart is needed. A root
key's id is a fingerprint (`rk_` + 16 hex of SHA-256), so the file needs no
metadata.

**Alternatives.** (a) A JSON file with explicit ids and timestamps. (b) A
directory of one-key files named by id, like a keystore.

**Trade-off.** No creation timestamps or provenance in the file; an
operator who wants an audit trail keeps it elsewhere (the keyring table
records which root key id wrapped each data key, which is the fact that
matters). Deleting the old line *before* rewrapping locks the keyring —
documented, and the error names the missing id.

**Why (simplicity).** It is the Kubernetes ordered-key-list pattern in a
form `cat` can read and `echo >>` can extend, with the same shape as the
existing `cluster_secret` file. Fingerprint ids remove a whole class of
"the id in the file doesn't match the id in the table" mistakes.

## 14. The config block is `encryption`; the CLI group is `legion keyring`

**Call.** A top-level `encryption = { enabled, rootKey, dataKeyRotationAge }`
block on the manager config, beside `workloadIdentity`, `acl`, `edgeBoot`;
and a top-level `legion keyring status|rotate|rewrap|root-key …|provider
test` command group.

**Alternatives.** `kvEncryption = {…}` next to `kvDebounceMs`, and
`legion kv keyring …` under the existing KV verbs.

**Trade-off.** The name promises more than v1 delivers — today the block
encrypts KV values only, and the doc has to say so in its first paragraph.

**Why (extensibility).** The keyring is a cluster facility, not a KV
feature: the follow-ups that encrypt derived columns or signing keys will
reuse it unchanged, and renaming a config block later is a migration for
every operator. Naming it for what it *is* now avoids that; naming it for
what it covers today would be wrong in one release.

The entries below were made while implementing the plan (2026-09-21). They
are ranked among themselves; each sits below the design-time calls above
because none of them constrains the public surface the way those do.

## 15. Keys already unwrapped stay usable until a restart

**Call.** `Keyring::load_rows` keeps every data key that is already unwrapped
in memory and only asks the provider for rows it has not seen. Consequently a
root key file that goes missing (or is replaced with the wrong key) while a
manager is running does not lock anything: reads and writes continue on the
keys in memory, and the loss bites at the next start, where nothing is in
memory yet.

**Alternatives.** Re-unwrap every row on every reload, so a lost file locks
the keyring within one reload (the plan's §6.7 table reads that way).

**Trade-off.** `legion keyring status` on a running manager can say
`unlocked` while the file on disk is already gone; the operator finds out at
the next restart, or from a joiner that receives no bundle. Tests that want
to observe a lock must restart the store (which is what
`a_missing_root_key_locks_reads_and_writes_but_not_deletes` does).

**Why (simplicity at 3am, and correctness).** The leader installs the key it
just generated directly into memory before the provider has necessarily
re-read the file, and the `exec` provider must never be called on the raft
apply thread; both fall out naturally when a reload is "unwrap what is new"
rather than "re-verify everything". And a running manager losing its ability
to serve KV because a file vanished under it is a worse incident than one
that keeps serving until someone restarts it on purpose.

## 16. Reads self-heal by reloading a local provider once before failing

**Call.** `Store::kv_entry_from_raw` retries a `KeyringLocked` read once after
`load_keyring()` when the provider is `file` or `env`. A data key that just
replicated in, or a root key that just appeared on disk, is one file read
away, so the read succeeds instead of failing until the next 15-second tick.

**Alternatives.** Fail the read and rely on the keyring loop's tick (plus the
wake on every replicated keyring change) to reload.

**Trade-off.** A read that is genuinely locked pays one extra file read
before it errors. `exec` providers get no such retry (a KMS call on a read
path is exactly what the design forbids) and rely on the loop.

**Why (ergonomics).** The docs promise "copy the file into place and the
next read works" with no restart; this is what makes that sentence true.

## 17. The upgrade gate reads a schema-version header on every transport reply

**Call.** Every `RaftTransport` reply carries `x-legion-schema-version` (the
answering build's migration count); the leader's network layer records it
per peer, and `voters_missing_schema_version` compares every voter against
`KEYRING_SCHEMA_VERSION` (pinned to the keyring migration by a test). A
voter that has never answered, or runs a build that predates the header, is
"missing", which fails closed.

**Alternatives.** (a) Put the version into raft membership metadata at join
time — but a member's version changes at every upgrade without a re-join.
(b) Add a dedicated peer-version RPC — another RPC to version.

**Trade-off.** The map is only as fresh as the last reply, so a freshly
elected leader sees every peer as missing until its first AppendEntries
round completes (milliseconds), and the keyring loop retries every 15
seconds. The header is a few bytes on every reply.

**Why (correctness with no new protocol).** The leader already talks to
every follower on every heartbeat; a reply header is free, needs no new RPC,
and is exactly as current as the cluster's own liveness.

## 18. The join flow delivers the root key in the first release, not Phase 4

**Call.** `JoinRaftClusterReply.root_key_bundle` shipped with everything
else: the leader seals its file/env root key material under
HKDF-SHA256(cluster secret) bound to the cluster id, and the joiner writes it
to its own key file only if none exists.

**Alternatives.** Ship Phases 1–3 first and let multi-manager operators copy
the file by hand for a release, as the plan's phasing said.

**Trade-off.** Anyone holding the cluster secret (the join token) receives
the root key by joining. That widens nothing — a joined manager receives the
whole database — and is stated in the doc. `exec` clusters get no bundle.

**Why (ergonomics, and the test suites demanded it).** "Join the cluster"
being one command is the headline promise, and the existing raft suites
(`raft_membership`, `raft_lanes`) read KV values on joiners after apply: with
encryption on by default they cannot pass without it.

## 19. `GetKeyringStatus` computes the next-step hint server-side

**Call.** The reply's `hint` field is one sentence chosen by the manager
(copy the root key from here; run `legion keyring rewrap`; waiting for
manager X to upgrade; nothing to do). The CLI and the UI print it verbatim.

**Alternatives.** Let each client derive advice from the structured fields.

**Trade-off.** English in an RPC reply, and a hint that cannot be localized
or restyled per client without a server change.

**Why (ergonomics for the average operator).** The person reading
`legion keyring status` at 3am wants the sentence, not the fields; putting
it on the server means every surface — CLI, UI card, MCP tool — says the
same thing, and the wording is tested once.

## 20. `env` root keys accept commas as line separators

**Call.** The `env` provider splits `LEGION_ROOT_KEY` on commas as well as
newlines, so a two-key rotation window fits in one environment variable.

**Alternatives.** Newlines only (identical to the file).

**Trade-off.** A base64 line can never contain a comma, so the split is
unambiguous; the cost is one more rule to document.

**Why (ergonomics).** Environment variables with embedded newlines are
awkward in systemd units, Kubernetes manifests, and shells; commas are not.

## 21. First-start initialization is a log line, not a scheduler event

**Call.** `ensure_keyring_initialized` logs the minted root key path and the
first data key id; it emits no `keyring.initialized` event. Rotation,
rewrap completion, root-key rewrap, lock/unlock transitions, and reset do
emit events.

**Alternatives.** Emit the event the plan listed, so the journal records
when encryption began.

**Trade-off.** No journal entry marks the moment a cluster started
encrypting; the manager log and `legion keyring status` (key creation
times) carry it instead.

**Why (simplicity, and it broke nothing else).** Every fresh store
initializes once at start, so the event would be the first row in every new
cluster's journal before any real work — and it shifted event ids and
counts in every test that reasons about the journal. The transitions an
operator actually acts on all stay as events.

## 22. A leader mints its root key before answering a join

**Call.** `root_key_bundle` (the join reply) mints the root key when the
`file` provider has none yet, instead of answering with an empty bundle.

**Alternatives.** Leave minting to the keyring maintenance loop and let a
joiner that arrived first fetch the key later (a new "pull the root key"
RPC), or document that operators must start the bootstrap manager alone
first.

**Trade-off.** The join handler now does a small piece of keyring work
(one file write, once per cluster) that otherwise belongs to the
maintenance loop.

**Why (simplicity/ease).** Every manager of a fresh cluster starts at once;
the first join can beat the loop's first tick. A joiner receives the root
key only with its join reply, so an empty bundle would leave it locked the
moment the first data key replicates — "join the cluster" would stop
being one command exactly in the default, zero-config path. `env` and
`exec` providers cannot mint and behave as before.
