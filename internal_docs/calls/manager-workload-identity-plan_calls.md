# Judgement Calls — Manager Workload Identity for State Replication

Plan: [`../plans/manager-workload-identity-plan.md`](../plans/manager-workload-identity-plan.md)

**Entries are ordered by project impact, highest first; an entry's number is its
rank.**

---

## 1. The manager presents a platform identity, and never issues one for itself

**Call.** "Extend workload identity to managers" is implemented as the
*consuming* half only. The manager reads a JWT that something else wrote to
disk, exchanges it for S3 session credentials, and refreshes it. Legion's own
OIDC issuer — the ES256 signer, JWKS, and rotation loop that already exist in
`src/manager/workload_identity.rs` — is deliberately not used for this.

```jsonnet
// what shipped
credentials: {
  provider: 'webIdentity',
  webIdentity: {
    tokenFile: '/var/run/secrets/eks.amazonaws.com/serviceaccount/token',
    roleArn: 'arn:aws:iam::123456789012:role/legion-manager-state',
  },
},

// what did NOT ship, and would have been ~80 lines given the existing signer
workloadIdentity: {
  managerIdentities: [
    { name: 'state-replication', audience: ['sts.amazonaws.com'], ttl: '15m' },
  ],
},
```

**Alternatives.** (a) A `managerIdentities` block mirroring `nodeIdentities`:
the manager mints itself a token with `legion.io/scope = "manager"`, AWS
validates it against the published JWKS. This is the obvious design, it reuses
machinery that already exists, and it makes the identity story uniform — *every*
Legion component federates through Legion. It is what the question as asked
literally proposes. (b) Both: ship the platform provider and the self-issued one,
let operators choose.

**Trade-off.** The bare-metal operator with no platform IdP gets nothing new
from this feature — they stay on static keys until they run something that
writes a JWT to a file (SPIRE, Vault's identity token backend). Alternative (a)
would have served them on day one with no new infrastructure. That is a real
cost and it is the strongest argument for the option that lost.

**Why (security boundary, and simplicity).** Three failures, all the same shape:

1. The ES256 private key lives in the `signing_key` table *of the store being
   backed up*. Store compromise would then imply backup destruction — and
   surviving control-plane compromise is the entire job of a backup.
2. `--restore-from` runs before any store exists, so there is no key, so there
   is no token. A self-issued identity can never serve disaster recovery, which
   means the operator keeps a static credential for exactly the scenario the
   feature exists for. It would delete no secrets; it would add a second
   mechanism beside the one it failed to replace.
3. STS validates the token by fetching the issuer's JWKS over public HTTPS —
   served by the manager. The manager's ability to write its own backup would
   depend on the manager being reachable, during precisely the incidents where
   it is not. (Kubernetes hits this and dodges it by hosting cluster OIDC
   discovery on S3 rather than the API server. Legion cannot: the JWKS is
   generated by the running process.)

The general rule, worth keeping: **an identity may not be issued by the system
it is used to protect.** Workers satisfy it — their node identity comes from the
manager, a separate trust root. The manager's own backup cannot satisfy it
against the manager's own IdP, by construction.

Alternative (b) was rejected on simplicity: shipping both means shipping a
footgun that works perfectly in steady state and fails at restore, which is the
worst possible failure schedule for a durability feature.

## 2. One credentials block outranks the two existing credential sites

**Call.** `persistence.streaming.credentials` is a single block that feeds both
the replica *and* the lease. Before this change the two were configured
differently and independently: the replica read `AWS_*`/`LITESTREAM_*` from the
process environment (rustyriver's URL semantics), the lease read literal keys
from `manager.jsonnet`.

Precedence is narrowest-wins: `lease.objectStorage` static keys still win for
the lease, then `credentials`, then `object_store`'s own resolution. But one
combination is a hard boot failure rather than a preference:

```
persistence.streaming.credentials.provider is 'webIdentity' but
persistence.streaming.lease.objectStorage still sets accessKeyId/secretAccessKey;
remove the lease keys so the lease uses the same federated credential as the replica
```

**Alternatives.** (a) Add `webIdentity` support to each site separately, leaving
the two configuration surfaces as they are — smaller diff, no precedence rules
to explain. (b) Make `credentials` unconditionally win and deprecate
`lease.objectStorage`'s keys outright.

**Trade-off.** A precedence rule is a thing to document and a thing to get
wrong, and (b) would have avoided it entirely — at the cost of silently changing
what an existing config authenticates as on upgrade. Two credential sources with
one override is more surface than one source, and it is the price of not
breaking anyone.

**Why (simplicity, on the operator's side of the line).** The failure this
prevents is real and quiet: rotate one credential, miss the other, and the
manager replicates fine while silently losing the ability to renew its lease —
or the reverse. It surfaces as a failover that does not happen. Refusing to boot
on the federated/static split turns a latent incident into a startup error with
both config paths named in it.

## 3. `environment` is the default and leaves the old code path literally untouched

**Call.** The default provider reproduces today's behavior, and does so by
returning `None` from `build_credential_provider` — which routes back through
`ObjectStoreClient::new(config)`, rustyriver's own store construction, byte for
byte. Legion only builds the store itself when a provider is explicitly
configured.

**Alternatives.** (a) Always build the store in Legion and implement an
env-reading provider for `environment` — more uniform, one code path instead of
two. (b) Make the default `AmazonS3Builder::from_env()`, which would give
everyone the full AWS chain (instance profile, `~/.aws/credentials`, and
`AWS_WEB_IDENTITY_TOKEN_FILE`) for free.

**Trade-off.** Two code paths where one would do, and a `build_replica_store`
that duplicates rustyriver's private `build_store` (bucket, region default,
path-style, endpoint/`allow_http`) — real duplication that will need to track
upstream if rustyriver changes those defaults. Accepted, and flagged in a
comment at the site.

**Why (blast radius).** (b) is tempting and is the more *useful* default — it is
also the one that silently changes which principal an existing cluster
authenticates as, on a restart the operator thought was a no-op. A durability
subsystem is the wrong place to be clever about defaults. The plan names a
future `default` provider as the honest way to offer the full chain to people
who ask for it. (a) loses to the same argument: an env-reading provider is
*nearly* the same as rustyriver's env lookup, and "nearly" is how back-compat
promises break.

## 4. Credential failures degrade the operation, not the process

**Call.** A failed STS exchange returns an error from `get_credential()`, which
fails that one object-store call. The replica sync loop already logs and retries
on the next tick; the lease loop classifies a renew error as `Retain` — keep the
lease, retry — so an STS blip does not trigger a spurious failover. Only
statically-checkable misconfiguration (missing `roleArn`, out-of-range
`durationSeconds`, missing sub-block) fails the manager at boot.

**Alternatives.** (a) Verify the credential at startup with a real exchange, and
refuse to boot if it fails. (b) Escalate repeated exchange failures into
relinquishing the lease.

**Trade-off.** A manager can boot into a configuration that will never
successfully replicate — a typo'd role ARN is only discovered at the first sync,
in a log line rather than at the terminal the operator is looking at. That is a
worse first-run experience than (a).

**Why (availability).** A manager that refuses to start because STS was briefly
unreachable is a manager that is down for a reason unrelated to scheduling.
Replication is asynchronous and already tolerates gaps by design; scheduling is
not, and does not depend on S3 at all. Making a control plane's liveness depend
on a cloud IAM endpoint inverts the dependency that streaming persistence is
supposed to have. (b) is worse still: it converts a credential problem into a
leadership change, which is the most disruptive possible response to the least
disruptive class of failure.

## 5. The token file is re-read on every exchange, never cached

**Call.** `WebIdentityCredentials` caches the *session credentials* (until
5 minutes before expiry) but re-reads the token file from disk on every
exchange.

**Alternative.** Read the token once at construction — it is a file on local
disk, and the provider is built once at boot.

**Trade-off.** A `read_to_string` on every refresh, i.e. roughly once an hour.
Not a real cost; listed because the alternative is what a reasonable
implementation does by default.

**Why (correctness).** Projected service-account tokens rotate underneath a
long-running process — EKS refreshes them well before expiry and the pod is
expected to notice. Caching the token bytes is *the* classic IRSA bug: it works
for the first day and then the workload starts failing with
`InvalidIdentityToken` at an interval nobody connects to the deploy. There is a
regression test asserting the second exchange sends the second token.

## 6. Redaction is asserted by tests, not maintained by review

**Call.** `Debug` is hand-implemented on both providers, and unit tests assert
on sentinel values that neither the token nor the secret key appears in `Debug`
output. `WebIdentityCredentials`'s `Debug` still prints the role ARN, token
*path*, and endpoint; `StaticCredentials` prints nothing at all, not even the
access key id.

**Alternative.** `#[derive(Debug)]` plus a code comment, which is what most of
this kind of code does, plus the existing repo rule against tracing secrets.

**Trade-off.** Six lines of `Debug` impl and a test per type, and a slightly
less useful `Debug` for anyone reading a stack trace.

**Why (security boundary).** `object_store::CredentialProvider` *requires*
`Debug`, so a derived one is one `error!(provider = ?self, …)` away from putting
a live session key in the log aggregator — and the `?` sigil is invisible in
review. The access key id is withheld from `StaticCredentials` too: it is half
of a secret pair and there is no diagnostic that needs it. AGENTS.md's tracing
rule ("never trace secrets/tokens") is a rule about intent; this makes it a
property of the type.

## 7. STS XML is scanned for four leaf elements, not modelled with serde

**Call.** `extract_elements` walks `quick-xml` events and pulls the first text
of each named element, matching on the local name so a namespace prefix cannot
break it. No `#[derive(Deserialize)]` response model.

**Alternative.** A serde model of `AssumeRoleWithWebIdentityResponse` —
type-safe, self-documenting, and what `object_store` itself does internally.

**Trade-off.** A flat scan cannot tell you *where* in the document a field
appeared, so a hypothetical response with two `<AccessKeyId>` elements in
different sections would take the first. No real STS response has that shape,
and the same function serves both the success and `<ErrorResponse>` bodies,
which a serde model would need two of.

**Why (robustness at the boundary).** The response is four leaf strings, and the
things that actually break XML deserialization at a provider boundary are
namespace prefixes, added elements, and non-AWS S3-compatible brokers with
slightly-off documents — all of which a scan survives and a strict model
rejects. It also degrades usefully: an HTML error page from a proxy yields
`Unknown: no message in STS response` and the HTTP status rather than a parse
error that hides the status.

## 8. `--restore-from` was left on the old credential path

**Call.** Phase 1 covers replication and the lease. `legion start manager
--restore-from` still takes a local path and is untouched.

**Alternative.** Ship restore in the same change — it is arguably the *most*
important consumer, since §1's whole argument turns on restore working without
Legion.

**Trade-off.** The disaster-recovery path an operator reaches for is still a
manual `rustyriver::restore` or an out-of-band `aws s3 sync`, with whatever
credential that tool finds. The feature's best argument is not yet its best
demo.

**Why (shippable phases).** Teaching `--restore-from` to accept a replica URL is
a new user-facing CLI surface with its own failure modes (partial restore,
existing-state collision, which generation to restore) and its own doc and
capability-catalog obligations. It is a phase, not a corner of this one. Phase 1
stands alone: it deletes static keys from the path that runs continuously. Named
as deferred in the plan (§9) and in `internal_docs/TODO.md` rather than left
implied.
